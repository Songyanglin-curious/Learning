# Java 日期与时间学习计划

创建日期：2026-11-10。

当前状态（2026-11-17）：**用户已主动提出以 Epoch 时间戳统一理解同一时刻的不同表示，并指出解析时需注意时区和夏令时；已有概念解释证据，未执行日期时间实验或评测。** 用户也曾概括“转成时间后都存时间戳”；已澄清 `Instant` 以 Epoch 秒及纳秒部分表达时刻、`Date` 以 Epoch 毫秒表达时刻，而 `LocalDateTime` 保存日期时间字段，不自动携带时区或变成时间戳。该类型边界的澄清尚无后续反馈，不据讲解认定掌握。

已讨论的使用边界：单一地区系统可以统一约定无偏移日期时间按北京时间解释，不必每个值重复携带偏移量；这属于外部契约，不是 `LocalDateTime` 自带的信息。服务器、数据库和接口即使服务中国用户，也必须保持解释一致。示例 `2026-11-17 08:00:00` 按 UTC+08:00 解释，对应 `2026-11-17T00:00:00Z`。用户已提出统一约定的合理性，后续又主动说明时区与夏令时在文本还原时刻时的作用。

文本格式边界（已讲解，待反馈）：ISO 8601 写法中的 `T` 仅分隔日期与时间，不表示时区；`Z` 表示 UTC 零偏移，等价于 `+00:00`。`2026-11-17T08:00:00Z` 对应北京时间十六点，而 `2026-11-17T08:00:00+08:00` 表示北京时间八点。不能为北京时间文本直接追加 `Z` 而期望仍表示原时刻。空格格式仍可按双方约定使用，解析器须匹配格式。

## 学习路线

### 一、先分清“时间”在表示什么

从“生日”“订单创建时刻”“每天上午九点”“经过半小时”这些例子入手：

- 日期、一天中的时间、当地日期时间、确定的时刻、时间长度有什么区别？
- UTC、时区、UTC 偏移量和时间戳分别描述什么？
- 时间戳的秒与毫秒单位怎样约定，为什么显示成文字还需要解释规则？

目标：看到时间字段时，先判断其含义和缺少的信息，再选择类型。

### 二、认识现代 Java 时间类型的分工

以 `java.time` 为主线，建立类型与需求的对应关系：

- `LocalDate`、`LocalTime`、`LocalDateTime` 各自保留哪些信息？为什么 `LocalDateTime` 不能单独确定全球时间线上的一个时刻？
- `Instant`、`OffsetDateTime`、`ZonedDateTime` 分别适合表达什么？
- 不可变对象的修改方法返回什么，为什么调用后需要接住结果？

目标：能够为生日、日志时刻、接口中的带偏移日期时间等需求选择类型，并说明理由。C# 的 `DateOnly`、`TimeOnly`、`DateTime`、`DateTimeOffset` 按当前疑问对照。

### 三、理解时区与转换边界

围绕“同一个时刻，在不同地区显示为什么不同”展开：

- `ZoneId` 与 `ZoneOffset` 的区别；地区时区为什么不仅是一个固定偏移量？
- 保持同一时刻转换显示，与保持钟表数字重新解释，有什么不同？
- 夏令时切换时，当地日期时间为什么可能不存在，或对应两个时刻？
- 系统默认时区会影响哪些操作，为什么换机器后可能得到不同结果？

目标：能追踪转换前后保留了什么，并知道歧义需要明确处理规则。具体地区的规则按需查阅，不背时区表。

### 四、理解日期运算与经过时间

围绕“明天”“一个月后”“经过 24 小时”展开：

- `Period` 的年月日与 `Duration` 的经过时间有什么区别？
- 加一天与加 24 小时为什么在带时区的场景中需要区分？
- 月末加月、闰年和跨年有哪些边界，需要查阅哪种调整规则？
- 比较日期时间时，比较的是当地字段还是同一时间线上的先后？
- 获取当前时刻与测量程序耗时分别需要什么能力？认识 `Clock` 和 `System.nanoTime()` 的用途即可。

目标：能够按需求选择运算与比较方式，避免把月份当固定天数，或把系统时钟差值直接当作可靠耗时。

### 五、把时间转换为文字，并在边界保留含义

围绕 `DateTimeFormatter`、解析与系统之间的数据交换展开：

- 时间对象与显示字符串有什么区别，格式化是否会改变其表示的时刻？
- 格式、语言地区、时区各自影响什么？
- 认识 `MM/mm`、`uuuu/yyyy/YYYY` 的含义差异，以及解析严格程度与非法日期的关系；不背完整格式符表。
- 文本没有偏移量或时区时，解析能够得到什么，哪些信息需要额外约定？
- 接口和存储边界怎样明确字段语义、时间戳单位、精度及偏移量／时区信息？

目标：能够判断数据是否足以恢复所需含义，不把所有日期时间一律当作 UTC 时刻。数据库与 JSON 工具的具体映射遇到需求再展开。

### 六、补齐旧代码阅读能力，再做场景回顾

- 认识 `Date`、`Calendar`、`SimpleDateFormat` 的职责、可变性、月份编号和线程安全陷阱。
- 知道新旧类型能够互转，并检查转换需要补充或可能丢失的信息；旧 API 的具体方法按需查阅。
- 用生日、订单日志、跨时区会议和每日本地固定时间这几个场景回顾选型与转换，不展开完整调度器实现。

目标：能够阅读和衔接旧代码，并为新需求优先考虑 `java.time`。不要求重新熟练掌握整套旧 API。

## 深入边界与接续位置

核心范围是时间语义、类型选择、时区转换、运算与文本边界。非 ISO 历法、闰秒细节、时区数据库维护、复杂周期调度、底层计时实现和性能优化，按实际问题深入。

**当前范围已由用户确认深度足够，专题收束（2026-11-17）。** 用户总结：准确解读数据携带的信息，有时区按时区、没有按约定，不当引入转换反而可能出错。已补充“业务约定不等于当前机器默认时区”的边界；未要求继续深挖或评测。该总结属于核心原则解释证据，不代表所有类型与操作已有独立应用证据。 用户对本地时间自述无问题，明确要求其他内容一次集中说明；已补齐下列常用能力。证据为讲解，示例未运行，未安排评测；不认定用户已独立应用或全面掌握。

- 类型与转换：`LocalDate` / `LocalTime` 保存日期或一天中的时间；`Instant` 表达时刻，秒／毫秒方法要区分；`OffsetDateTime` 携带固定偏移，`ZonedDateTime` 使用地区规则。`withZoneSameInstant` 保持时刻改变当地表示；无需强制将全部业务转为 UTC 存储。
- 运算边界：`Period` 表达日历年月日，`Duration` 表达时间长度；月末加月可调整至目标月最后一天。带夏令时时，加一天不保证等于经过 24 小时。`System.nanoTime()` 差值用于测量耗时，不是 Epoch 时间戳。
- 格式与解析：已讲 `parse` / `format`、空格格式、默认输出省略零秒、`MM/mm`、`HH/hh`、`uuuu/yyyy/YYYY` 及严格解析。现代核心时间类型与 `DateTimeFormatter` 不可变且线程安全，修改操作返回新对象。
- 旧 API：`Date` 表达 Epoch 毫秒时刻，其默认文本显示使用系统默认时区；`Calendar` 月份从零编号；`SimpleDateFormat` 非线程安全。`Date` 与 `Instant` 可互转，转成 `Date` 丢弃毫秒以下精度。
