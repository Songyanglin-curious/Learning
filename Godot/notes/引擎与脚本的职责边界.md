# 引擎与脚本的职责边界

2026-11-17 整理；Godot 4.x 的能力判断模型。用户明确将理解边界、形成判断能力置于手写脚本熟练度之前。本笔记保存已讲解的模型，不表示已验证用户能独立完成节点选型。

## 核心模型

不是“引擎负责显示、脚本负责逻辑”。引擎本身包含物理、输入、动画、布局、计时等大量逻辑。更准确的分工是：

- 引擎提供并执行通用机制。
- 节点、资源及场景配置承载能力选择和参数。
- 开发者决定游戏规则、组织对象，并配置或编写驱动行为。

“开发者决定”不等于“必须写脚本”：动画轨道、节点参数、编辑器信号连接等也能表达部分行为。脚本通常调用、组合引擎已有能力，并补充项目特有的决策与状态。

## 自动执行与显式调用

引擎有某能力，不代表所选节点会自动执行该能力。节点选型也在选择谁掌握控制权。

| 任务 | 引擎责任 | 开发者责任及边界 |
| --- | --- | --- |
| Sprite2D 旋转 | 回调调度、保存变换、按结果绘制 | 决定速度、条件并修改角度；也可以改用动画轨道，无需同一段旋转脚本 |
| RigidBody2D 球下落与反弹 | 按配置进行物理运动、碰撞检测与响应 | 配置形状、质量、材质与层/掩码，按需要施加力或冲量；一般不在普通帧回调中持续直接改位置，与求解器争夺控制权 |
| CharacterBody2D 玩家撞墙 | 提供运动与碰撞滑动求解方法 | 解释输入、决定速度、调用 MoveAndSlide；不是加了角色节点就自动获得键盘移动和重力规则 |
| Area2D 进入区域加分 | 按监测、形状、层/掩码等条件检测重叠并提供信号 | 决定什么算金币、加多少、是否销毁、如何防止重复计分 |
| Control 游戏结束 UI | 布局、绘制、按钮输入与信号 | 决定何时判负、显示什么、重玩重置哪些状态 |

普通 Sprite2D 直接改 Position 表示改变变换，并不意味着请求了一次带阻挡的物理移动。图片穿墙可能是没有使用碰撞移动机制，而不是引擎碰撞系统失效。单独显示图片也不会自动获得碰撞体。

以上是职责示例，不替代具体节点 API 契约；实际行为还受启用状态、节点是否入树、回调时机和项目配置影响。

## 判断一个需求的方法

先问：引擎是否已有承担这项机制的节点、资源或方法？有则优先配置和组合，不重新实现通用物理求解、计时或动画插值。

再问：它会自动运行，还是需要调用？前提是什么？输入和输出是什么？它不知道哪些游戏规则？

最后检查控制权：谁负责更新位置、速度或状态？不要让物理引擎、动画与脚本无意中同时写同一个状态。发生问题时按节点选型、配置、调用/时机和游戏规则分别定位，而非只盯脚本语法。

## 与脚本语言选择的关系

GDScript 与 C# 操作同一套引擎机制；差别主要在语言执行环境、绑定、类型转换、工具链、对象管理和发布边界，不是各自拥有一套物理引擎。引擎机制通用地学，实现细节按 C# 绑定查。

## 语言怎样接入同一个引擎

语言绑定把原生引擎的对象、方法、属性、回调和信号映射为某种语言可用的形式。一般是在同一游戏进程中交互，不是进程间网络请求；但同进程不表示对象表示相同或能调用任意内部函数。

| 接入 | 执行与边界 |
| --- | --- |
| GDScript | 内置执行系统与语言集成，调用暴露的原生引擎功能 |
| C# | 编译后的托管代码由 .NET 执行，经 Godot C# 绑定访问原生对象，必要时转换数据 |
| C++ GDExtension | 原生共享库由引擎加载，通常通过 godot-cpp 包装及 GDExtension C 接口接入，仍受公开接口限制 |
| C++ 引擎模块/源码修改 | 与引擎一起编译，可更深接触内部实现，但需维护自定义引擎构建；不等同于普通扩展 |

C# 旋转表达式 `RotationDegrees += DegreesPerSecond * (float)delta` 同时包含不同边界：自动属性 DegreesPerSecond 的读取和乘法属于托管计算，而 RotationDegrees 的读取与写入经绑定访问原生节点。不能把每个 C# 字段访问都算作引擎调用，也不能把原生节点属性当作纯托管字段。

交互是双向的：脚本调用引擎方法/属性；引擎通过语言集成调用 _Process 等回调；信号通知已连接处理函数；导出元数据使编辑器认识可配置属性。引擎并非自动理解任意普通类的全部用途。

“等价”要分层：相同公开 API 在相同前提下通常具有相同的功能契约，最终由同一引擎子系统处理；不保证调用成本、类型表示、对象管理、部署支持或内部访问深度相同。GDExtension 不等于直接访问全部 C++ 内部实现；C# 不是先翻译为 GDScript；也不把每次绑定调用都泛化为字符串反射。

## 调用开销不等于异步延迟

普通引擎属性访问和许多方法调用是同步的：C# 进入绑定、访问原生节点，调用返回后才执行后续语句。跨语言会有绑定、检查或数据转换成本，但不天然多等待一帧，也不天然成为异步队列。具体仍以 API 契约为准，不把所有引擎接口概括为立即完成全部效果。

例如先设置 RotationDegrees = 90，再读取该属性，在无其他逻辑介入时可读到设置后的状态；但屏幕呈现仍需后续渲染、GPU 与刷新流程。状态写入完成和画面可见是两个时刻。物理方法返回也不代表所有后续物理步进及碰撞结果都已完成。

CallDeferred 明确安排稍后调用，QueueFree 明确安排稍后释放；这是接口时序，不是绑定通信不及时。实际精确执行时机需查对应 API，不从“稍后”直接推断固定下一帧。

性能上关注高频重复跨边界，而不是仅凭使用 C# 推断慢。可先读原生属性，在托管局部变量中批量计算，再写回一次，减少往返；但中间各次写入若有必须发生的副作用，合并可能改变语义。未做当前项目性能测量，不提供固定耗时或语言速度保证。

判断时依次区分：同步返回契约、子系统生效时机、显示链路、调用频率与实际测量。
