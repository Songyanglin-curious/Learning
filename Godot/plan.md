# Godot .NET 学习计划

## 目标与学习起点

独立使用 Godot .NET（C#）开发一款小体量 2D 游戏：能创建项目、组织场景、选择节点、编写和连接行为、运行、定位问题，并形成可继续迭代的开发方法。不是遍历全部功能，也不是依靠逐步照抄完成演示。

用户已确认没学过 Godot；有 C#/.NET、面向对象和常见开发流程经验（用户自述，不重新考试或重复开基础课），主要使用 VS Code。没有已验证的 Godot 理解或实践能力。工具环境的实测证据与当前接续只维护在[进度快照](progress.md)。

主要来源与阅读边界见[官方资料导航](index.md#官方资料地图与导航)。以指定介绍入口建立认知，渐进式教程建立使用基础，第一个 2D 游戏承担受指导整合，再以不同任务验证独立迁移。

## 目标深度与能力证据

- L1 认知：知道能力、用途、限制与查阅入口。例如渲染器大类、导入流程概貌、不采用功能的存在。
- L2 理解与判断：能解释机制、预测变化、判断边界。例如生命周期顺序、碰撞选型、场景依赖、资源共享。
- L3 实践：能在适度变化的任务中独立配置、实现、诊断或设计。例如建立场景、接入 C#、实现游戏循环和修复问题。

核心机制要求 L2，常用工作流程要求 L3；不要求记全 API 或脱离文档手写所有代码。允许查官方文档与使用 AI，但要能解释关键决定、验证行为并修正错误。理解、在提示下做成、独立迁移分别收集证据，不互相替代。

## 范围与取舍

必需覆盖：引擎整体模型、编辑器基础、场景树与实例、资源与引用、C# 构建与绑定、节点生命周期、信号、2D 坐标与输入、移动和碰撞、基础动画、UI、生成与释放、游戏状态、运行与调试，以及桌面导出基本流程。

暂不系统深入：3D、着色器、复杂渲染、多人网络、引擎源码、性能专项、复杂 AI、编辑器插件、MCP、第三方框架。TileMapLayer、Camera2D、Autoload、存档只在实际玩法或组织需要时展开，不把它们作为所有小体量游戏的必修前置。美术以占位或官方资源为主，不把素材制作扩成第二条课程线。

暂以 Windows 桌面实践为工作假设，不替用户锁定最终发布平台或游戏题材；在独立作品选题前确认。无固定时长、日程、打卡、复习周期或课时数。

## 能力依赖与组织理由

1. 先理解编辑器负责组织什么、引擎运行什么、C# 扩展什么，才有办法判断操作结果，而非背按钮。
2. 节点与单场景运行是场景复用的前置；场景实例和资源引用是理解“改了一个为什么影响多个”的前置。
3. 场景树和运行实例是理解节点生命周期、访问节点和通信的前置。普通对象构造不等于节点已就绪；普通 GC 经验不等于引擎对象释放语义。
4. 生命周期与 C# 构建、节点引用支持脚本行为；再补信号连接、发射和连接清理，才能建立可重用的交互对象。
5. 回调、输入动作、向量/时间步进、坐标空间支持移动；物理对象、形状、层与掩码支持可靠交互。只改位置不等于获得碰撞阻挡。
6. 可交互的独立对象与可靠通信支持游戏循环；UI 是并行展示分支，基础动画与音效服务于状态反馈，不必等学完全部 2D 手册。
7. 可运行完整循环之后，用未照做的需求检验设计和诊断能力，再检查导出后能否运行，避免把编辑器内成功当作完整交付。

这是一张依赖说明，不是强制解锁顺序。查文档、运行观察、排错从第一个单元开始，C# 实际断点在接入脚本时建立，后期再综合使用。

## 完整阶段路线

| 阶段 | 核心问题、重点与深度 | 实际任务 | 能力要求与测评 |
| --- | --- | --- | --- |
| A 整体认知与最小运行 | 游戏怎样由节点/场景组成；编辑器、项目、运行实例的区别；信号先认知 L1，整体模型 L2，基础操作 L3 | 创建原生 2D 学习项目，用无脚本场景展示文字或图像，运行当前场景与项目 | 能从编辑器找到节点属性、资源和文档；解释项目入口及当前场景；换一个场景仍能判断运行哪个，不只重复按钮顺序 |
| B 场景复用与资源 | 场景蓝图、实例、组合、覆盖与恢复；局部/全局坐标的初步模型；资源共享 L2，实例操作 L3 | 一个可见对象场景在主场景中放多个实例；分别改变源场景、实例属性、共享资源，观察作用范围 | 先预测再验证哪些实例改变；能区分实例字段独立与资源可能共享；将对象移到另一容器后仍可复用，说明边界 |
| C C# 与引擎运行机制 | 节点脚本与程序集、partial/回调/Export、构造与入树就绪/退出、节点引用、帧循环、信号与释放；机制 L2，构建和诊断 L3 | C# 驱动可调参数的可见行为；Button/Timer/自定义信号组成小交互；动态增加和释放对象；验证一次断点 | 能解释回调与引用时机，独立接线并防止重复订阅；定位一个构建或节点路径问题；不把托管引用仍存在当作原生节点仍有效；信号断连例外按需实验 |
| D 2D 输入、运动与交互 | 坐标与向量、Input Map、delta、处理/物理回调、Area/Body/Shape、层与掩码、简单动画；选型与时间机制 L2，玩法实现 L3 | 小房间内移动、墙壁阻挡和一个触发区域，加入最小视觉反馈；不先做完整游戏 | 能说明检测与阻挡差别，选择合适对象；诊断错误 mask 或速度单位；预测并验证帧率变化和斜向输入的行为，避免重复乘 delta |
| E 从交互对象到完整游戏 | 参考官方第一个 2D 游戏整合玩家/敌人/主场景/HUD、Timer、生成回收、得分与状态重置；组织 L2，整合 L3 | 以 C# 完成受指导的小型游戏循环，再加入一个非照抄的小需求；UI 基础布局、音效按玩法需要加入 | 开始、游玩、失败、重玩均正确；连续重玩不遗留敌人、计分或订阅；能追踪谁发信号、谁管理状态；把对象放到新场景仍可测试 |
| F 独立小作品、调试与交付 | 需求收敛、场景责任、运行时观察、VS Code 断点/日志/远程场景树、导出与资源；独立工作流 L3，性能分析仅 L1/按需 | 从需求而非逐步教程实现一个小型 2D 变体或新作品，控制为单个核心玩法；导出 Windows 包并离开编辑器测试 | 自主拆分场景和节点选型，完成一项新需求、定位一个实际缺陷并给出因果证据；启动/结束/重玩可靠；导出包可运行且素材许可可说明 |

独立作品验收不以代码行数或功能数量计分：关键是需求能落到引擎结构、机制能解释、行为有证据、错误能定位、查资料后能继续做。教程作品可作为练习载体，但照做成功本身不判为独立应用。

## 近期三个教学单元

只细化现在足以确定的三个单元，后续按表现拆分或合并。下面是教学设计，不表示本次已经讲授、操作或布置作业。

### U1：Godot 如何把一个项目变成运行中的画面？

**归属与前置：** 阶段 A；不要求任何 Godot 经验，只使用已有编程认知建立对照。

**能力目标：** 能说清项目、场景、节点与运行入口的关系；知道 Godot 与 VS Code 各自负责什么；能够完成创建、保存、运行、停止的最短闭环。信号仅认识用途，不展开委托声明。

**官方阅读：** 介绍中的简介、关键概念、界面；设计理念只取场景组合；随后读[节点与场景](https://docs.godotengine.org/zh-cn/4.x/getting_started/step_by_step/nodes_and_scenes.html)中创建与运行的相关部分。学习资料使用方式从“学习新特性”提取，不安排整篇背诵。

**组织方式：** 先以一个小型 2D 游戏的可见对象建立整体认知，再在编辑器定位场景面板、检查器、文件系统、2D 工作区、运行与输出。按实际界面讲解，不要求当前版本和截图逐项一致。

**计划实践：** 教学开始后由学习者创建一个不带脚本的场景，显示一段文字或图像；修改一个可见属性并观察；增加第二个场景作为对照，验证“运行当前场景”和“运行项目”的区别。本轮不执行这些操作。

**验证方式：** 能解释“打开了另一个场景，为什么运行项目仍是原来的画面”，并通过检查主场景与当前运行入口证实；能独立找回一个属性和相应官方帮助。只做成不等于已稳定理解。

**易混淆与取舍：** 场景不是只等于关卡；场景树不是 C# 类继承树；引擎已安装不等于 C# 构建/断点已经验证。本单元不写移动代码、不讲碰撞配置。

### U2：如何复用对象，又不让一次修改意外影响全部对象？

**归属与前置：** 阶段 B；需要能保存场景、添加节点并运行观察。

**能力目标：** 理解源场景与实例、实例属性覆盖、资源引用的区别；能选择修改源场景还是单个实例；知道资源共享是另一个维度，而非“所有东西都是深拷贝”。

**官方阅读：** [创建实例](https://docs.godotengine.org/zh-cn/4.x/getting_started/step_by_step/instancing.html)正文；重点是蓝图、实例覆盖与资源 Make Unique 提示。官方弹球项目作为可选观察材料，不以其物理细节作为前置。资源更深层的复制规则到实践时查对应官方说明，不预先泛化。

**计划实践：** 使用自己能理解的可见对象场景创建多个实例；改变源场景的默认属性，再覆盖一个实例并恢复；按需要加一个共享资源/独立资源的对照，先预测影响范围再观察。全程可以不用脚本。

**验证方式：** 给出新的修改需求，让学习者判断应改哪一层并验证；将同一对象放入另一容器场景仍能使用；解释“两个节点实例不同，为什么一个资源的修改可能同时可见”。

**易混淆与取舍：** 场景实例不是 C# 类实例概念的简单同义替换；节点父子关系不等于类型继承。源场景更新不能无条件覆盖实例已有覆盖值。本单元不引入复杂场景继承体系、依赖注入框架或 Autoload。

### U3：C# 如何接入节点，并在正确的时机改变行为？

**归属与前置：** 阶段 C 的起始单元；需理解运行中的场景由节点实例组成。信号与动态释放作为阶段 C 后续单元，不塞进第一次脚本接入。

**能力目标：** 知道脚本挂在哪里、引擎如何调用它、什么时候可查找子节点；能完成编辑→构建→运行→观察；区分构建失败、引用错误和行为逻辑错误。

**官方阅读：** [第一个脚本](https://docs.godotengine.org/zh-cn/4.x/getting_started/step_by_step/scripting_first_script.html)中的 C# 页签与 [C# 基础](https://docs.godotengine.org/zh-cn/4.x/tutorials/scripting/c_sharp/c_sharp_basics.html)的工作流；生命周期精确定义在教学前核读 Node 类参考，不照搬教程对 Ready 的简化表述。

**组织方式：** 仅解释 Godot 特有的 partial 节点脚本、文件/类名、生成工程、构建更新、Export 和回调；对照构造、EnterTree、Ready 的时机，使用最小日志观察父子顺序；Process 与 PhysicsProcess 先区分调度目的，物理移动细节留给阶段 D。

**计划实践：** 在可见节点挂 C# 脚本，以日志观察就绪与帧回调，加入一个检查器可调参数来控制简单旋转；用节点引用改变一个子节点的可见属性；验证构建和运行，并在获得配置修改授权后验证一次 VS Code C# 断点。未来实践给完整必要的节点结构与 C# 实现，不要求手动翻译 GDScript。

**验证方式：** 解释为什么“对象已构造”不能证明子节点可用；根据一次节点改名/路径失配定位问题；修改参数并说明实际值来自代码默认还是检查器；能借助错误输出判断构建没有更新还是运行行为错误。断点是否命中单独记录，不能由扩展已安装推出。

**易混淆与取舍：** 不把 Ready 简化为每次重新加入都自动执行；不把 SDK 9、运行时 9 与项目目标框架混为一谈；新导出属性通常需重建后才在编辑器出现。不重讲类、循环、继承或普通 C# 事件语法。

## 测评和路线调整

每阶段选择有代表性的解释/预测、变化任务与故障诊断，结合实际作品观察，不为每个术语固定安排实验或考试。采用同一判断原则：能否说明关键机制，能否在变化后继续使用，能否以观察证据解释不符预期的行为。

如果解释清楚但操作不熟，只补操作；能照做但解释与预测失败，缩小实验补核心模型；在变化任务中反复表现稳定，再保守记录“能够应用”。关键前置存在真实错误时回补；尚未验证不代表禁止继续，未答题也不构成强制入口。AI 生成代码可作辅助，但学习者需能验证、判断和修改关键逻辑。
