## 一、字节、文字与流分别是什么

文本保存到文件时，要按编码规则转换为字节；从文件读成文字时，要按相应规则把字节解码。以“中”为例，UTF-8 编码后的字节是 `E4 B8 AD`，共三个字节。

输入、输出以程序为参照：输入是读进程序，输出是从程序写出。

| 数据层次 | 输入抽象 | 输出抽象 | 负责什么 |
| --- | --- | --- | --- |
| 字节 | `InputStream` | `OutputStream` | 提供或接收原始字节，不负责解释成文字 |
| 字符 | `Reader` | `Writer` | 提供或接收字符；连接文件等字节来源／目标时，需要相应的解码／编码层 |

字节流也能处理文本文件。原样复制文本时，不需要知道文字含义，复制字节即可；检查文件头同样属于字节处理。读日志、逐行分析配置、生成文本等任务，使用字符读写通常更方便。

Java 的 `Reader`／`Writer` 以 `char` 为处理单位。`char` 是 UTF-16 码元，不等于所有情况下的一个完整 Unicode 码点或一个用户看到的字符；相关长度区别已在字符串笔记中说明，本轮不另行展开。

流提供逐步读写的能力，允许分批处理，但不保证一定不加载全部内容。既有以文件为来源的流，也有以内存数组为来源的流；调用流的 `readAllBytes()` 也可以累积全部剩余内容。

## 二、字节读取与解码是两层分工

`InputStreamReader` 把字节输入流包装成字符输入流；`OutputStreamWriter` 则把字符编码后交给字节输出流。

```java
Path path = Path.of("D:\\Learning\\data.txt");

// 打开字节流，并使用 UTF-8 解码成字符；结束后自动关闭资源
try (Reader reader = new InputStreamReader(
        Files.newInputStream(path),
        StandardCharsets.UTF_8)) {

    int value = reader.read(); // 读取一个 char；-1 表示结束
    if (value != -1) {
        System.out.println((char) value);
    }
}
```

假设文件使用 UTF-8，且第一个文字是“中”：

- 底层字节流从文件提供字节。
- 外层 `InputStreamReader` 按 UTF-8 解释字节，向业务代码提供字符。
- 两层处理同一条数据流，不是各自读取一遍文件，也没有因此打开第二份文件。

实际实现可能预读，不应把一次 `reader.read()` 理解成底层只读取一个字节，或恰好只读取组成该字符的几个字节。

本轮对两层分工的理解可以保留为：底层读取字节，外层加一层“翻译”，把字节解释为字符。写入方向反过来：字符先编码成字节，再交给底层输出。

## 三、分批读取不保证对齐文字边界

“中”的三个 UTF-8 字节可能被分在两批中：

| 批次 | 字节 |
| --- | --- |
| 第一批 | `E4 B8` |
| 第二批 | `AD` |

如果两批分别调用 `new String(bytes, UTF_8)`，每次都当作一份独立的完整输入，那么第一批缺少末尾字节，第二批也不能独立组成这个文字。错误解码后再拼接字符串，不能修复原先丢失或替换的信息。

正确的处理需要让解码状态跨批次保留：保留尚未完成的字节序列，拿到后续字节再继续。持续使用同一个 `InputStreamReader`，就可以把这层管理交给它，而不是对每批字节重新独立解码。

因此，分批读字节与逐块独立转字符串不是同一件事。用于文本读取时，应保留连续的解码过程。

## 四、整体读取与分批处理的区别

整体读取指方法返回前准备好全部结果，不代表底层只发生一次读取。例如 `Files.readString(path)` 内部可以多次读取，但调用者拿到的是整份文本。

分批处理则允许取得一部分后就开始处理，不必等待完整输入。批次既可以是固定大小的字节块／字符块，也可以是行或业务记录。

以统计日志中包含 `ERROR` 的行数为例：

```java
long errorCount = 0;

// 逐行统计，只保留计数，不保存已经处理过的日志
try (BufferedReader reader =
        Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String line;
    while ((line = reader.readLine()) != null) {
        if (line.contains("ERROR")) {
            errorCount++;
        }
    }
}
```

数据经过的过程是：取得当前行 → 判断并更新计数 → 继续下一行。旧行若没有其他保留引用，就可以被垃圾回收，不需要一直保存到文件读取结束。

`BufferedReader` 内部会缓冲，逐行读取不代表每行都单独访问一次磁盘。具体缓冲机制留到第三条主线解释。

## 五、内存取决于数据怎样组织和保留

本轮确认的关键认识是：**怎么读提供处理能力，怎么组织和保留数据决定内存需求。** 读取方式仍有自身开销，例如整体读取必然要保留完整结果；分批读取则提供限制当前处理规模的条件。

| 使用方式 | 持续保留什么 |
| --- | --- |
| 整体读为 `String` | 全部文本 |
| 逐行统计数量 | 当前行、读取缓冲、一个计数 |
| 逐行读取但不断加入列表 | 所有已经保留的行 |
| 分批读取但不断追加到 `StringBuilder` | 不断增长的完整文本结果 |
| 边读边筛选，直接写到另一个文件 | 当前处理单元及输入输出缓冲 |

只看这条处理链路，可以将内存需求理解为：读取／解码缓冲，加上当前处理单元、持续保留的结果和尚未处理完的数据。

需要记住几条边界：

- 仍被列表、缓存、队列等保留的数据，GC 不能因为“处理过了”就回收。不再需要且不可达的数据才可以回收，也不保证立即回收。
- 分批读取后全部拼接，并没有消除最终完整结果的内存需求；扩容和结果转换还可能产生额外开销。
- 逐行处理的当前单元大小取决于最长行，不是固定大小。某行特别长，`readLine()` 仍可能构造很大的字符串；按记录处理同样受单条记录大小影响。
- 读取后交给后台任务，如果读取更快且队列没有上限，待处理数据仍会在内存中积压。需要同时控制排队规模和处理速度。
- 磁盘文件大小不等于 Java 中的精确内存占用，还要考虑解码表示、对象与临时数据。

选择依据是业务是否需要同时持有全部数据，以及数据规模是否可控。小配置整体读取方便；大日志统计、筛选导出、文件转换等可以边读边处理。若业务确实要返回完整列表或完整字符串，最终结果本身的内存需求仍然存在。

## 六、编码选择不是编码识别（待回顾）

先用读写双方的关系理解：

| 文件生成时使用的规则 | Java 读取时指定的规则 | 含义 |
| --- | --- | --- |
| UTF-8 | UTF-8 | 按与生成方一致的规则解释字节 |
| GBK | UTF-8 | 强行把 GBK 字节当作 UTF-8 解释，不是先正确读出 GBK 再转换成 UTF-8 |

例如 `Files.newBufferedReader(path, StandardCharsets.UTF_8)` 的意思是“按 UTF-8 读取”，不是“检查文件使用什么编码，再自动选择”。解码器拿着已经选定的规则工作，判断该选什么规则是另一个问题。

普通文本不一定记录生成时的编码名称，同一批字节也可能符合多种编码。例如 `41 42 43` 在 UTF-8、ASCII、ISO-8859-1 下都是 `ABC`，不能单凭它唯一确定生成方的编码。自动检测只能结合可用线索判断，不能保证对所有文件都确定正确。

选错规则有两类表现：

- 字节在所选编码下仍合法：可以得到字符串，但文字可能错误，也就是乱码；没有异常不证明选对了编码。
- 字节在所选编码下不合法或无法映射：按照 API 与错误策略报告异常、替换或忽略。

`CharsetDecoder` 可配置 `REPORT`、`REPLACE`、`IGNORE`；常见替换字符是 `�`。这里只认识策略，不要求记配置方法。`Files.newBufferedReader` 遇到非法或无法映射的字节序列时，在读取过程中报告 `IOException`。

不传编码参数也不代表自动识别：

| 写法 | 编码来源 |
| --- | --- |
| `new InputStreamReader(input)` | Java 默认字符集，不是对该文件检测出的结果 |
| `Files.newBufferedReader(path)` | 固定使用 UTF-8 |
| `Files.readString(path)` | 固定使用 UTF-8 |

实际依据优先来自生成方与读取方的约定、外部系统的格式说明或导出设置。来源不明时可以尝试检测或人工指定，但要保留不确定性。严格报错能发现部分不合法输入，不能证明所有成功解码的文本都选择了正确编码。

本节下一次若仍有疑问，先只区分“按指定编码解释字节”和“推测原始编码”，暂不扩展更多探测器或配置。
