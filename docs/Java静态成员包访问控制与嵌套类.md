# Java 静态成员、包、访问控制与嵌套类

## 静态成员：类型级的状态与操作

实例字段属于具体对象，每个对象各有一份；静态字段属于类型，由该类型的实例共享，没有实例也能使用。静态方法不需要当前实例，因此没有 `this`，但可以通过显式取得的对象引用操作实例。

从组织方式理解，静态成员为共享状态和不依赖具体实例的操作提供类型归属，并纳入访问控制。例如累计计数可以是静态字段，数学计算可以是静态方法。

“全局唯一”只是近似理解：静态成员不一定公开，Java 同名类由不同定义类加载器加载时也可以分别拥有静态字段。当前先以“属于类型，而非某个对象”理解即可。

- `static` 不等于常量，静态字段可以变化；`final` 字段不能再次赋值，但引用指向的对象未必不可变。
- 静态方法不参与实例方法的重写与动态分派；子类的同签名静态方法属于隐藏。
- 统一通过类名访问静态成员，归属更清楚。
- 可变的共享状态仍需考虑并发和调用方之间的影响，静态不自动提供线程安全。

### 演变脉络与静态类

C 的 `static` 早于面向对象，涉及静态存储期限、内部链接等含义；C++ 的静态成员把共享状态和不依赖对象的操作组织到类下面。Java、C# 中，静态成员的核心含义是属于类型。这个脉络帮助理解关键字，不代表各语言中所有 `static` 用法完全相同。

Java 没有 C# 的顶层 `static class`，但不妨碍普通类声明静态字段和方法。纯工具类通常使用私有构造方法，并可加 `final` 禁止继承。C# 静态类还会由编译器禁止实例成员；Java 工具类写法没有这项同等约束。

至于 Java 为什么没有增加对应的顶层类语法，本次没有确认到足以说明完整决策过程的一手历史材料。“现有机制已经能表达大部分需求”是合理解释，不应写成已证实的设计动机。

## 包：逻辑归属、目录组织与类型查找

### 三个层次分别看

| 层次 | 作用 |
| --- | --- |
| 语言层 | 源文件的 `package` 声明决定类型属于哪个包，并参与同包访问控制 |
| 源码组织层 | 标准项目布局通常让源码根目录下的路径对应包名 |
| 运行层 | 常规基于目录或 JAR 的类加载器按类名映射的资源路径查找字节码 |

例如 `Account.java` 声明 `package com.example.bank;`，其完整类名是 `com.example.bank.Account`。标准源码路径通常是 `源码根目录/com/example/bank/Account.java`，常规字节码查找路径是 `com/example/bank/Account.class`。

源码根目录本身不属于包名，例如 `src/main/java` 通常只是源码根目录。

每个普通 `.java` 文件分别声明包，不是在入口统一声明。一个文件内的多个顶层类型共用该文件的包声明。不声明时属于未命名包，简单实验可以使用，正式项目通常采用具名包。

### 包名层级不传递权限

`com.example` 和 `com.example.bank` 是两个不同的包。目录有父子关系，但子包不自动取得父包的包级访问权限；`import com.example.*` 也不导入子包中的类型。

包名中的层级用于命名和归类，不意味着包之间有权限继承。

### 为什么目录映射令人不灵活

同一逻辑包的文件，完全可以有“只通过子文件夹分类、不改变包归属”的组织需求。Java 语言层面并不简单禁止这种需求：显式把源文件交给 `javac`，通过 `-d` 输出时，可以按声明的包生成标准字节码目录。

但常规 Java 工具体验围绕源码目录与包路径一致展开。于是，在同一源码根目录内，为了分类而建立子目录，通常也会拆出子包，改变类型完整名称及包级访问边界；不拆包则容易平铺大量文件。

这是实际的灵活性代价。名称到路径的映射让源码查找、字节码定位和工程组织更统一，但不能据此认为源码必须使用相同布局：编译器可以把其他源码布局转换为标准输出布局。

同一包还可以分布在多个源码根目录下，例如主源码与测试源码，所以“一个包绝对只能放在一个物理目录”并不准确。具体 IDE、构建工具对偏离标准布局的支持需要分别验证，不能笼统认定 Maven、Gradle 一律不能构建。

关于早期设计者怎样权衡全部利弊，本次没有取得完整决策史证据。名称到路径映射的机制是事实，历史取舍的完整动机不能只靠现有规则倒推。

### 与 C# 的关键区别

| 职责 | Java 常规组织方式 | C# |
| --- | --- | --- |
| 类型命名与分组 | `package` | `namespace` |
| 源文件分类 | 通常对应包路径 | 可以独立于命名空间，也常按约定对应 |
| 内部访问边界 | 包级访问以包为边界 | `internal` 主要以程序集为边界 |
| 常规运行时类型定位 | 类名映射到目录或 JAR 中的字节码资源路径 | 通过程序集和类型元数据解析，不按 namespace 为每个类寻找文件夹 |

Java 提供更统一的映射，C# 更便于独立调整物理目录与逻辑分组。只是整理文件夹时，C# 可以不改 namespace；Java 标准布局往往同时改变 package。这是不同层次耦合程度的差异。

### import、JAR 与 Spring Boot

- `import` 简化类型名称，不安装依赖、不复制代码，也不绕过访问权限。类型重名时可以使用完整名称；Java 没有 C# 式类型别名导入。
- 同包类型以及 `java.lang` 中可访问的类型通常不需显式导入。
- 包不等于 JAR：一个 JAR 可包含多个包，普通 classpath 中一个包也可能分散在多个 JAR；模块化时存在进一步限制。
- Spring Boot 不要求 Controller、Service 分包。它们可属于同包，也可按职责或业务分包；文件夹名称本身不决定组件身份。
- 默认组件扫描通常从 `@SpringBootApplication` 所在包向子包查找。这是框架扫描规则，不意味着子包拥有同包访问权限。
- 改包名是类型重构，可能影响引用、反射中的类名字符串与扫描配置，不能仅当作移动文件。

## 访问控制

顶层类可以是 `public` 或不写访问修饰符，不能声明为 `private`、`protected`。普通类的字段、方法、构造方法可以使用四种权限：

| 修饰符 | 当前类内部 | 同包其他类 | 跨包子类 | 跨包普通类 |
| --- | --- | --- | --- | --- |
| `private` | 可以 | 不可以 | 不可以 | 不可以 |
| 不写（包级访问） | 可以 | 可以 | 不可以 | 不可以 |
| `protected` | 可以 | 可以 | 有条件可以 | 不可以 |
| `public` | 可以 | 可以 | 可以 | 可以 |

表格按普通类理解；同一个顶层类内部的嵌套类型还可以互访私有成员。成员访问也受所在类型是否可访问等条件限制；模块系统还可能施加额外边界，后续再学。

Java 与 C# 的基本访问控制概念相近，主要留意：

- Java 不写修饰符通常是包级访问，不是 C# 普通类成员默认的 `private`。
- Java `protected` 允许同包访问，不要求继承关系；C# 不因同命名空间就授予 `protected` 访问权限。
- 跨包子类访问父类的 `protected` 实例成员时，不能借助任意父类类型引用访问；通常通过自身或该子类类型（含其派生类型）的引用访问。
- 构造方法的权限控制构造入口；跨包子类可通过 `super(...)` 调用受保护父类构造方法，不代表可以随意直接 `new` 父类。

访问修饰符建立语言边界，边界内的业务代码负责维护业务规则。

## 成员内部类与静态嵌套类

两者都把一个类型定义在另一个类中。区别在于：普通成员内部类实例关联一个具体外部实例，静态嵌套类实例没有这一步自动关联。

```java
class Player {
    private boolean playing;

    class Controller {
        // 启动当前控制器所关联的播放器
        public void play() {
            Player.this.playing = true;
        }
    }

    static class Settings {
        int volume;
    }
}
```

```java
Player p1 = new Player();
Player p2 = new Player();

Player.Controller c1 = p1.new Controller();
Player.Controller c2 = p2.new Controller();
c1.play(); // 修改 p1 的状态
c2.play(); // 修改 p2 的状态

Player.Settings settings = new Player.Settings();
```

可以把普通成员内部类的关联理解成自动记住一个外部对象引用，类似普通类通过构造方法传入并保存依赖；这是语言机制，不是依赖注入框架。

`Player.this` 表示当前内部类对象所关联的那个播放器。`p1.new Controller()` 明确选定 `p1`，并不是创建一个新的播放器。

`new Player.Settings()` 中，`Player.Settings` 是类型名称，创建的只有 `Settings` 对象。这里 `static` 表示不自动关联外部实例，不是 C# 的静态类，不禁止创建实例或声明实例成员。

| 对比 | 普通成员内部类 | 静态嵌套类 |
| --- | --- | --- |
| 是否关联具体外部实例 | 是 | 否 |
| 创建 | `p1.new Controller()` | `new Player.Settings()` |
| 访问外部实例状态 | 可直接访问所关联对象的状态 | 需要显式取得对象引用 |
| 是否能有自己的实例成员 | 可以 | 可以 |

C# 普通嵌套类不会自动关联外部实例，在这一点上更接近 Java 静态嵌套类。

### 选择与代价

没有外部实例依赖时，优先考虑独立类或静态嵌套类。需要依赖就显式传入，通常更直观。

普通内部类适合完全服务于某个外部对象的实现细节，例如需要操作所属集合状态的迭代器。它的便利伴随更紧的耦合：依赖可能不明显、可直接访问外部私有状态，内部对象被长期保留还可能连带保留外部对象。

不是静态嵌套类必须传依赖，而是它不会自动获得外部实例；实际需要什么，再显式提供什么。

局部类、匿名类等写法留到实际遇到时补充。
